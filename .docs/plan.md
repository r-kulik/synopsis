S06 может разрабатывать архивирование на стабильных fixtures параллельно UI. Его окончательный gate проходит после появления реальных результатов S04/S05; моковые данные не доказывают сквозную переносимость. S05 может начинаться до завершения визуальной карты, но сквозное создание карточки принимается только на интегрированной карте.

## Организация параллельной работы

1. S00: интегратор и три ограниченных субагента — Markdown selection, геометрия карты, хранение/архив.
2. S01: один владелец контрактов; остальные могут независимо ревьюить, но не менять общий API параллельно.
3. S02: один владелец основы приложения; UI-проектирование на fixtures допускается только без конфликтующих изменений.
4. После S02: редактор S03, карта S04 и перенос S06 — три исполнителя плюс интегратор.
5. После S03: его слот занимает S05; карта и перенос продолжаются при стабильных контрактах.
6. S07: интегратор связывает модули; субагенты исправляют дефекты только в назначенных областях.
7. S08: независимый проверяющий возвращает замечания; авторы исправляют, проверяющий повторяет затронутые сценарии.

Максимум в этой сессии — четыре активных агента, включая интегратора. Не запускать больше трёх исполнителей одновременно. Параллелить независимые области, а не конкурентную правку схемы, lockfile или маршрутизации.

## Правило перехода

У каждого этапа есть входной gate, проверяемые результаты и выходной gate. Интегратор проверяет фактическое состояние и отчёт; сообщение исполнителя «готово» не открывает следующий этап автоматически. Незавершённый критерий либо исправляется, либо остаётся явно открытым. Требование не снимается ради завершения этапа.

Этапы фиксируют отчёты в `.docs/reports/Sxx-report.md` по [шаблону](agents/report-template.md). Сейчас этих отчётов нет: нельзя заранее создавать их как выполненные.

## Общий Definition of Done этапа

- Scope и назначенные FR/AC реализованы; внеплановые изменения перечислены и обоснованы.
- Проверки соответствуют риску, реальные команды и результаты записаны.
- Данные пользователя и соседние области кода сохранены; нет конфликтов интеграции.
- Контракты/документация обновлены только при фактических изменениях.
- Нет заглушек, выдаваемых за завершённый пользовательский сценарий.
- Известные ограничения и необходимые решения названы явно.

## Порядок приоритетов

Сначала доказать корректность Markdown, независимость конспекта от карты и переносимость. Затем обеспечить удобную ежедневную работу и полное отображение карты. Опциональные backlinks, дополнительные стили и оптимизации сверх принятого размера курса выполняются после обязательных сценариев. Генерацию, совместную работу, сворачивание, разделы и встроенный PDF не добавлять ни на одном этапе без нового пользовательского решения.
