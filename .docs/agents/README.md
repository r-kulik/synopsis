# Работа интегратора и субагентов

Пользователь прямо предложил субагентов для разработки. Это разрешает распределять ограниченные задачи; не означает разрешение на публикацию, покупку компонентов или внешние действия от имени пользователя.

## Обязанности интегратора

1. Прочитать применимые `AGENTS.md` и документацию продукта; проверить текущее состояние репозитория.
2. Выбрать ближайший готовый по зависимостям этап из [плана](../plan.md).
3. Перед началом сообщить пользователю комментарий из документа этапа, адаптировав его к фактам текущей работы.
4. Назначить одному исполнителю конкретную область владения; передать путь документа этапа, стартовый промпт и известные решения.
5. Выполнять собственную полезную работу: общие контракты, интеграцию, воспроизведение проверок и разрешение зависимостей.
6. Проверить diff и gate каждого исполнителя; обновить статус этапа в отчёте, а не объявлять готовность по одному сообщению.

При общей рабочей директории изменения агента сразу видны всем. Изолированные worktree допустимы при принятой стратегии интеграции, но не обязательны. Агент не откатывает и не перезаписывает чужие изменения. Общие файлы всегда имеют одного владельца.

## Обязательный контекст назначения

Каждый промпт из `prompts/` — стартовое задание, а не гарантия неизменности репозитория. Интегратор добавляет:

- Точный этап и принятые решения/ADR.
- Готовые зависимости и реальные команды запуска/тестов.
- Разрешённые пути, запрещённые общие файлы, имя владельца соседнего модуля.
- Ожидаемые FR/AC и путь отчёта.
- Текущие незавершённые изменения, с которыми нельзя конфликтовать.

Если этих сведений ещё нет, исполнитель сначала изучает состояние и предлагает точные границы, не меняя все модули самостоятельно.

## Области владения

| Владелец | Изменяет | Не меняет самостоятельно |
| --- | --- | --- |
| Интегратор | Схемы, публичные контракты, маршрутизация, зависимости/lockfile, миграции | Пользовательские требования без нового решения |
| Редактор | Markdown/render/selection, компоненты конспекта, свои fixtures | Доменные типы карты, archive schema |
| Карта | Карточки, контейнеры, рёбра, геометрия, стили/фильтры | Канонический Markdown, внутренний формат ссылок |
| Хранение/перенос | Адаптеры сохранения, asset I/O, import/export | UX создания сущностей и семантику удаления без интегратора |
| QA | Проверки, воспроизведения, отчёт о дефектах | Массовые исправления чужих модулей без переназначения |

Точные каталоги определяются на S01. Таблица описывает ответственность, не существующую сейчас структуру кода.

## Общие правила исполнителя

- Прочитать `.docs/README.md`, требования, модель, решения и свой этап полностью.
- Проверить входной gate до реализации. Не писать код поверх воображаемого API.
- Использовать существующие библиотеки; не писать собственный редактор или диаграммный движок без доказанной необходимости.
- Не добавлять AI, разделы, совместную работу, PDF-viewer, сворачивание или автоматические рёбра из ссылок.
- Не превращать карточку в единственное место хранения конспекта.
- Сначала согласовать с интегратором изменения общего контракта и зависимостей. Это внутренняя координация, а не необходимость спрашивать пользователя о каждом техническом шаге.
- Тестировать реальные риски и пользовательские сценарии; не выдавать макеты за интеграцию.
- Отчёт должен содержать реальные команды и результаты. «Должно работать» не является проверкой.
- Не создавать новых субагентов без назначения интегратора, если это приведёт к превышению слотов или дублированию работ.

## Граница пользовательских уточнений

Рутинные решения реализации интегратор принимает самостоятельно и записывает в ADR. Если прототип показывает невозможность выполнить согласованный UX без существенного ограничения, представить пользователю конкретное воспроизводимое ограничение и варианты. Не заменять пользовательское требование молча и не останавливать независимые задачи из-за нерешённого соседнего вопроса.

## Итог этапа

Исполнитель использует [шаблон отчёта](report-template.md). Интегратор принимает работу только после проверки обязательных AC и интеграционных последствий. Независимый reviewer получает конкретный diff/модули и ограниченную задачу, а не повторную реализацию этапа.
